# basalt 導讀（給初學者）

這份文件用白話解釋 basalt 在做什麼、為什麼這樣做，讓你可以在面試時把這個專案講清楚。不需要先懂資料庫內部，遇到名詞會先用生活中的例子說明。

## 一、它解決什麼問題

你平常用的 PostgreSQL、MySQL 是「資料庫伺服器」：程式透過網路把 SQL 送過去，伺服器負責把資料存到硬碟、在多人同時修改時不打架、當機後資料不會壞掉、把查詢算得又快又對。

basalt 是**從零開始用 Go 寫的一個資料庫伺服器**。它最特別的地方是：它講 PostgreSQL 的「網路語言」（wire protocol），所以真正的 PostgreSQL 工具——命令列的 `psql`、Go 的 `pgx`、Python 的 `psycopg`——**不用改任何一行**就能連上它，連 `\d 資料表` 這種指令都會印出跟 PostgreSQL 一模一樣的畫面。

但是 PostgreSQL 本身的程式碼一行都沒用到：硬碟上怎麼放資料、記錄檔怎麼寫、當機怎麼救回來、SQL 怎麼解析、查詢怎麼規劃，全部是自己寫的（大約兩萬九千行 Go）。目的不是取代 PostgreSQL，而是證明「我真的懂資料庫裡面每一層在做什麼」，而且每一個說法都有可以執行的測試佐證。

## 二、七個關鍵觀念（附生活比喻）

### 1. 分頁與緩衝池：書和書桌

資料庫檔案被切成一頁一頁（每頁 8 KiB），就像一本很厚的書。硬碟很慢，所以要讀的頁會先搬到記憶體裡的「緩衝池」，就像把常翻的書頁影印放在書桌上。書桌空間有限，滿了就用「時鐘演算法」挑一張最近沒用到的收回去；如果那張上面有改過的筆記（髒頁），收回前要先抄回書裡。

每一頁開頭都有一個檢查碼（CRC-32C），讀回來時驗算，紙被撕壞（頁面損毀）就能立刻發現。

程式在哪：`internal/storage/pool.go`、`page.go`

### 2. 預寫式日誌（WAL）：先記帳再搬錢

如果改資料改到一半停電，硬碟上就會留下一半舊一半新的爛資料。解法是「先寫日誌，再改資料」：任何修改都先寫一筆記錄到日誌檔（只會一直往後加，很快），確定日誌寫進硬碟後才算數。之後就算停電，重開機時照著日誌「重播」一遍就能把資料補齊。就像會計先記帳、再實際搬錢；帳本在，錢就對得起來。

「確定寫進硬碟」這件事在 macOS 上要用 `F_FULLFSYNC`，因為一般的 `fsync` 只把資料送到硬碟的快取，不保證真的落地。這個步驟很慢（約 4 毫秒），所以 basalt 做了「群組提交」：同時要提交的多筆交易共用一次 fsync，像電梯一次載很多人。

程式在哪：`internal/storage/wal.go`、`internal/vfs/sync_darwin.go`

### 3. 迷你交易：一次搬家要一次完成

有些動作會同時改好幾頁，例如 B+ 樹「分裂」一個節點要改三、四頁。如果日誌只記到一半就停電，樹就壞了。basalt 用「迷你交易」：把這幾頁的修改包成**一筆**日誌記錄，要嘛整筆重播、要嘛整筆不算，像搬家時把東西全部裝上同一台卡車，不會只到一半。

另外，檢查點（checkpoint）之後第一次改某一頁時，會把整頁的完整影本寫進日誌。萬一停電時那一頁剛好寫到一半（「撕裂的頁」），重播時用完整影本整頁覆蓋就好。

程式在哪：`internal/storage/mtr.go`、`store.go`（`Checkpoint`、`recover`）

### 4. 多版本並行控制（MVCC）：每個人看自己的照片

很多人同時讀寫時，最簡單的做法是上鎖排隊，但這樣讀的人會擋住寫的人。basalt 用 PostgreSQL 的做法：修改一列資料時不是覆蓋，而是**新增一個新版本**，舊版本標記「被誰刪掉」。每筆交易開始時拍一張「快照」（記下當下哪些交易已經提交），之後只看快照裡算數的版本。

比喻：大家看的是同一份文件在不同時間點的「照片」，有人在改文件不會讓你手上的照片變動。讀的人永遠不用等寫的人。

這也讓當機復原變簡單：沒提交的交易留下的新版本，在提交紀錄（commit log）裡查不到「已提交」，所以自動被當成作廢、看不見，之後由 VACUUM 清掉。不需要另外寫「撤銷（undo）」的流程。

程式在哪：`internal/txn/txn.go`（`Visible`、`Snapshot`）、`internal/storage/clog.go`

### 5. 兩種隔離等級與死結偵測：排隊規則

- **REPEATABLE READ（快照隔離）**：整筆交易用同一張照片。如果你要改的那一列，在你拍照之後被別人改掉並提交了，你會收到錯誤 40001（「先改的人贏」），應用程式要重試。
- **READ COMMITTED（預設，跟 PostgreSQL 一樣）**：每一條 SQL 重新拍照。遇到上面那種衝突時，basalt 會把這條 SQL 已經做的修改收回，換一張新照片重做一次，所以大家排隊等就好、不會報錯。

如果甲等乙、乙又等甲，就是「死結」，兩個人會永遠等下去。basalt 每次要等待時都會畫出「誰在等誰」的圖，發現繞成一圈就讓最後加入的那一方失敗（錯誤碼 40P01）。

程式在哪：`internal/txn/lock.go`、`internal/executor/dml.go`（`lockRow`）

### 6. B+ 樹索引：字典的部首索引

要在一百萬列裡找 `id = 77777`，一列一列掃太慢。B+ 樹像字典的索引：從最上層的目錄一路往下翻，三、四次就找到。basalt 把每個值轉成「可以直接比大小的位元組」（例如負數要把正負號位元翻轉），再接上那一列的位置，所以同一棵樹不用管型別就能比較。節點滿了就分裂、太空了就和隔壁合併。

程式在哪：`internal/storage/btree.go`、`internal/types/encode.go`

### 7. 查詢規劃器：導航軟體選路線

同一個 SQL 可以有很多種執行方法：先掃哪張表、用不用索引、兩張表用「雜湊」還是「排序合併」還是「巢狀迴圈」來接起來。規劃器像導航軟體：先把 SQL 轉成邏輯計畫，做一些一定有利的改寫（例如把 `WHERE` 條件盡量往下推、把常數先算好、把「對每一筆訂單都去查一次明細」的相關 `EXISTS` 子查詢改成一次做完的 semi join），再用 `ANALYZE` 收集來的統計數字（每欄有多少種值、分布直方圖）估計每條路線的成本，挑最便宜的。`EXPLAIN` 會把選中的路線印出來，格式跟 PostgreSQL 一樣。

程式在哪：`internal/planner/`（`binder.go` 解析名稱、`rewrite.go` 改寫、`optimize.go` 選路線、`cost.go` 估成本）

## 三、程式碼導覽（哪個檔案做什麼）

| 目錄 | 做什麼 |
|---|---|
| `cmd/basalt/main.go` | 伺服器程式進入點：讀參數、開資料庫、開始接受連線 |
| `internal/pgwire/` | 和客戶端講 PostgreSQL 協定：登入、送查詢、回傳結果、COPY、取消 |
| `internal/engine/` | 一個連線就是一個 Session：交易開始結束、DDL、ANALYZE、VACUUM、假的 `pg_catalog` 系統表 |
| `internal/sql/` | 把 SQL 文字切成單字（`lexer.go`），再組成語法樹（`parser.go`、`ast.go`） |
| `internal/planner/` | 語法樹 → 邏輯計畫 → 改寫 → 實體計畫，以及 EXPLAIN 的輸出 |
| `internal/expr/` | 運算式、內建函式（`funcs.go`）、聚合函式（`agg.go`），以及把運算式編譯成 Go 函式（`eval.go`） |
| `internal/executor/` | 真正執行計畫：掃描（`scan.go`）、連接（`join.go`）、排序聚合（`ops.go`）、新增修改刪除與約束（`dml.go`）、VACUUM（`maint.go`） |
| `internal/txn/` | 交易編號、快照、可見性判斷、鎖與死結偵測 |
| `internal/catalog/` | 有哪些表、欄位、索引、約束、統計資料 |
| `internal/storage/` | 緩衝池、日誌、迷你交易、資料頁、B+ 樹、提交紀錄、當機復原 |
| `internal/vfs/` | 檔案系統抽象：真的硬碟，以及測試用的「會故意弄丟或撕裂寫入」的假檔案系統 |
| `internal/types/` | 各種資料型別的值、文字與二進位格式、轉型、索引用的位元組編碼 |
| `test/` | 用真的 psql 跑的測試、Python 測試、SQLite 官方測試集、和 sqlite3 對答案、強制殺掉伺服器的當機測試 |
| `bench/` | TPC-B 壓力測試和分析型查詢的效能比較 |

建議閱讀順序：先看 `internal/storage/mtr.go`（迷你交易，最核心），再看 `internal/txn/txn.go` 的 `Visible`（MVCC 的判斷只有十幾行），然後 `internal/planner/optimize.go` 的 `planJoinRegion`（選連接順序），最後 `internal/pgwire/server.go` 看一個查詢從網路進來到結果送回去的路徑。

## 四、怎麼證明它是對的

- **真的客戶端**：`test/psql/run.sh` 用真的 psql 跑一份腳本，輸出要和事先存好的答案一字不差；pgx 和 psycopg 各有一組測試。
- **別人出的考題**：SQLite 官方的 sqllogictest 題庫，挑了 57 個檔案、38 萬多題，通過 99.98%。沒過的題目大多是 PostgreSQL 和 SQLite 本來規則就不一樣的地方（例如整數溢位，PostgreSQL 會報錯、SQLite 不會）。
- **和別人對答案**：亂數產生表格和四萬條查詢（8 個種子各 5,000 條，包含相關的 EXISTS、NOT EXISTS、IN 子查詢），同時丟給 basalt 和 sqlite3，結果完全相同。
- **真的殺掉它**：一邊有四個客戶端在轉帳，一邊隨機用 `kill -9` 殺掉伺服器，重開後檢查：有回報成功的交易一筆都不能少、回滾的不能出現、總金額不能變。跑 30 輪全部通過。
- **模擬停電**：假檔案系統會隨機丟掉還沒 fsync 的寫入、或把一頁寫一半，復原後檢查資料和 B+ 樹結構。

## 五、面試可能會被問的十個問題

**1. 為什麼要先寫日誌再改資料？**
因為日誌是循序追加、很快，而且一筆記錄可以描述好幾頁的修改。只要日誌在硬碟上，停電後重播就能把資料頁補回來；反過來先改資料頁，停電時就可能留下改一半的頁，沒有辦法知道原本長怎樣。

**2. 你的當機復原為什麼不需要 undo？**
因為用了 MVCC。沒提交的交易寫的是「新版本」，舊版本還在；復原後提交紀錄裡它不是「已提交」，可見性規則就讓那些新版本對所有人隱形，等 VACUUM 清掉。PostgreSQL 也是這樣做的。

**3. 撕裂的頁（torn page）怎麼處理？**
檢查點之後第一次改某一頁，就把整頁影本寫進日誌。復原從檢查點開始重播，遇到的第一筆就是整頁影本，直接覆蓋，壞的那半頁就不重要了。每頁也有檢查碼，可以偵測沒被修好的損毀。

**4. 快照隔離會發生什麼異常？**
寫入偏斜（write skew）：兩筆交易各自讀了同一批資料、各改不同的列，合起來違反規則（例如值班醫生最後變成零人）。basalt 有測試示範這件事。要防止它需要 SERIALIZABLE（SSI），basalt 沒有實作，所以要求 SERIALIZABLE 時會直接報錯而不是偷偷降級。

**5. READ COMMITTED 遇到衝突時你怎麼處理？和 PostgreSQL 有什麼不同？**
basalt 把這條 SQL 已做的修改收回，用新快照整條重做。PostgreSQL 是只針對衝突的那一列重新檢查條件（EvalPlanQual）。兩者保證一樣，我的做法不需要維護版本之間的指標，代價是衝突很多時會重做比較多工作。

**6. 死結怎麼偵測？為什麼選那個交易當犧牲者？**
每次要等待鎖時，從自己出發沿著「等待誰」的邊做深度優先搜尋，繞回自己就是死結。選「最後加入、造成循環的那個請求」失敗，因為不需要額外計算，而且結果固定、好測試。

**7. 規劃器怎麼決定用不用索引？**
用 ANALYZE 的直方圖和最常見值估計條件會留下幾列，再估成本：循序掃描是「頁數 + 每列一點 CPU」，索引掃描是「樹的高度 + 符合的列數 × 隨機讀一頁的成本」（basalt 的隨機讀成本預設是 1.1，PostgreSQL 是 4，因為資料通常已經在緩衝池或 SSD 上）。條件很挑（例如只剩 1%）就用索引，否則整張掃比較快。測試裡有驗證這兩種情況。

**8. 為什麼欄位用「編號」而不是「第幾欄」？**
因為規劃器會調換連接順序、把條件往下推，每個運算子輸入的欄位排列都會變。用全查詢唯一的編號，就不必在每次改寫時重新對位置；而某個運算子找不到的編號，一定是外層查詢傳進來的值（相關子查詢），處理起來很自然。

**9. psql 的 `\d` 是怎麼做到的？**
psql 其實是送一般的 SQL 去查 `pg_catalog` 系統表。basalt 沒有為 psql 寫特例，而是用自己的目錄即時產生假的 `pg_class`、`pg_attribute`、`pg_index`、`pg_constraint` 等表，再實作 psql 會呼叫的幾個 `pg_*` 函式，讓那些查詢走正常的解析、規劃、執行流程。

**10. 這個系統最大的效能瓶頸是什麼？你會先改哪裡？**
持久化提交受限於 `F_FULLFSYNC` 的延遲（約 4 毫秒），靠群組提交分攤；分析型查詢是一次處理一列的迭代器，在大部分查詢上比 SQLite 慢 1.2 到 3.2 倍。我已經做了子查詢去相關化（把 EXISTS 變成 semi join）和 numeric 的 64 位元快速路徑。接下來我會先做：在兩次 VACUUM 之間清理頁面裡的失效版本（像 PostgreSQL 的 page pruning），以及把 B+ 樹改成 B-link 樹，讓多個寫入者可以同時改同一個索引。

一個學到的教訓：去相關化剛做好時，Q4 反而慢了一倍。原因不在執行器，而在成本估計：規劃器把 `o_date >= a AND o_date < b` 兩個條件當成獨立事件相乘，估出來的列數多了五倍多，又把每次重複的索引查詢都當成要讀硬碟，結果選了比較慢的雜湊連接。修好估計之後才選對計畫。

## 六、自己動手試

```sh
make build
bin/basalt -D ./data -listen 127.0.0.1:5433
# 另開一個終端機
psql -h 127.0.0.1 -p 5433 -U me -d demo
```

進去之後可以試 `CREATE TABLE`、`\d`、`EXPLAIN ANALYZE`、開兩個 psql 視窗同時 `BEGIN` 改同一列，看看誰會等誰。
